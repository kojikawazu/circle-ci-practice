# CircleCI ルール

**「変更した内容に関係のあるジョブだけを動かす」** を原則とする。ドキュメントやルールの更新でテスト一式を回さない（無料枠クレジット・実行時間の浪費、キュー待ちの発生を防ぐ）。

## 設定ファイルの書き方

- 設定は `.circleci/config.yml` に集約し、**`version: 2.1`** を使う。
- **複数 job で同じ手順を繰り返さない。** `commands:` に切り出して再利用する（例: pnpm セットアップ + 依存インストール）。同じ `run` を 3 回書きたくなったら `commands:` へ（`duplication.md`）。
- **ツールのバージョンを固定する。** Docker イメージは `cimg/node:22.14` のようにタグを明示し、`latest` を使わない。pnpm は `packageManager` の値と一致させる（**片方だけ上げるとローカルと CI が食い違う**）。
- **job は「速く落ちる順」に並べる。** 依存は `requires` で宣言し、軽い検証（型チェック・UT）を重い E2E の前段に置く。
- `.circleci/config.yml` を変更した PR では、**その設定自体が通ることを CI で確認する**（設定変更は必ず CI を回す）。

## キャッシュ

- **キャッシュキーはロックファイルの `checksum` を含める**（`pnpm-v1-{{ checksum "pnpm-lock.yaml" }}`）。内容が変わらない限り再利用され、変われば新しいキーになる。
- **キャッシュは同じキーへ上書きできない。** 保存内容の意味を変えたら、キー先頭のバージョン（`v1` → `v2`）を上げる。
- **フォールバックキー（接頭辞のみのキー）を併記する。** 完全一致が無くても直近のキャッシュから差分インストールできる。
- **キャッシュに検証対象を入れない。** ビルド成果物・テスト結果をキャッシュ経由で持ち回ると、古い成果物でテストが通る事故が起きる。job 間で成果物を渡すなら `persist_to_workspace` / `attach_workspace` を使う（**同一 workflow 内でのみ有効**）。

## 変更内容と実行対象

| 変更内容 | 型チェック / UT | E2E |
|---|---|---|
| アプリケーションコード（`apps/**`, `packages/**`） | ✅ | ✅ |
| テストコード | ✅ | ✅（該当レベルのみ） |
| `.circleci/**` | ✅ | ✅ |
| 依存関係（`pnpm-lock.yaml`） | ✅ | ✅ |
| `docs/**`, `*.md`, `.claude/**` | ❌ | ❌ |

- **ドキュメント変更でも「何も動かさない」にはしない**。markdown のリンク切れ確認のような軽量チェックは実行してよい。
- **判定条件は「除外リスト」で書く**（`docs/**` `.claude/**` `*.md` 以外はアプリ変更とみなす）。「対象リスト」で書くと、**新しいディレクトリが増えたときに黙ってテストが走らなくなる**。安全側に倒す。

## パスによる出し分け（重要な落とし穴）

CircleCI には GitHub Actions の `paths-ignore` に相当するワークフローレベルの絞り込みが無い。実現手段は 2 つある。

| 手段 | 内容 | 注意 |
|---|---|---|
| **動的コンフィグ**（`path-filtering` orb + `continuation`） | setup workflow で変更パスを判定し、必要な job だけを含む設定を生成して継続実行する | 組織設定で dynamic config を有効化する必要がある |
| **job 内での早期終了** | job は常に起動し、変更が対象外なら `circleci-agent step halt` で中断する | 起動コスト（コンテナ確保・checkout）は掛かるが、設定が単純 |

- **GitHub のブランチ保護で必須チェックにしている job は、「起動しない」形にしてはならない。** job が起動しないと必須チェックは **`pending` のまま完了せず、PR がマージできなくなる**。必須チェックにする job は**常に起動させ、中身だけスキップする**（`halt`）。
- 必須チェックにしない job は、起動そのものを止める方が安価。

## デプロイ

- **デプロイは `main` への push（＝ PR マージ）を唯一のトリガとする。** `filters.branches.only: main` を明示し、PR ブランチから本番へデプロイしない。
- 本番デプロイ job には **`context` と承認ゲート（`type: approval`）** を置く。シークレットは context 単位で管理し、fork PR から参照させない。
- シークレットは CircleCI の環境変数 / context で渡す。**`config.yml` に直接書かない**（`git.md` の push 禁止物）。

## 結果の可視化

- 失敗調査に必要なものは **`store_artifacts`** で残す（Playwright の HTML レポート・スクリーンショット・trace）。
- テスト結果は **`store_test_results`**（JUnit XML）で渡し、UI 上で失敗テストを特定できるようにする。
- **CI が落ちた状態を放置しない。** `main` が赤いまま次の作業を始めない。

## レビュー観点

- ドキュメント・ルールのみの PR で、テスト一式が起動していないか。
- 逆に、**アプリコードを変更したのに必要な job がスキップされていないか**（判定条件の書き漏れ）。
- 必須チェックにしている job が、起動そのものを止められていないか（PR がマージ不能になる）。
- イメージタグ・ツールバージョンが固定されているか。
- 同じ `run` ブロックが複数 job にコピーされていないか（`commands:` へ切り出す）。
